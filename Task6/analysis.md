# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:
   - Кто: system:serviceaccount:secure-ops:monitoring
   - Где: namespace kube-system
   - Почему подозрительно: нарушение принципа минимальных привелегий. Попытка получения секретов из сервисзной учетной записи одного namespace в другом.

2. Привилегированные поды:
   - Кто: minikube-user
      Что делал: создан pod с флагом securityContext.privileged = true
   - Комментарий: Pod с таким признаком могут управлять кластером и изменять его состояние изнутри. Может быть замаскированной атакой на систему.

3. Использование kubectl exec в чужом поде:
   - Кто: system:serviceaccount:secure-ops:monitoring
   - Что делал: попытка выполнить команду "cat /etc/resolv.conf" в системном pod `coredns`
   - Почему подозрительно: попытка получить системные настройки кластера не мониторинговой учетной записью.

4. Создание RoleBinding с правами cluster-admin:
   - Кто: minikube-user
     Что делал: создан объект RoleBinding/escalate-binding для роли cluster-admin. Тем самым выдав права cluster-admin для serviceaccount monitoring
   - К чему привело: повышение уровня доступа для мониторинг учетной записи. 

5. Удаление audit-policy.yaml:
   - Кто: minikube-user 
   - Возможные последствия: сокрытие следов противоправных действий, отключение аудита

## Вывод

На данный момент RBAC в кластере позволяет делать больше чем нужно. Следует переработать права в соответствии с принципами наименьших привелегий.
Рекомендации по возникшим инцидентам:
1. Учетной записи "monitoring" следует ограничить права через RoleBinding только на namespace "secure-ops"
2. В целом необходима ревизиия всех учетных записей и их уровня доступа
3. Права на создание привелегилированных pod не должно быть ни у кого, кроме администраторов кластера
4. Прав на любые действия в namespace "kube-system" не должно быть ни у кого, кроме администраторов кластера
